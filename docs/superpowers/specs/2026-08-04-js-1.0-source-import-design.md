# Snyk VulnBench JS 1.0 Source Import Design

**Status:** Approved  
**Date:** 2026-08-04  
**Upstream:** <https://github.com/snyk-labs/snyk-vulnbench-js-1.0>  
**Imported commit:** `7c944ea438a31ea4cbd6803f1bb9560d01f932e5`

## Context

This repository is the canonical, durable website for the VulnBench initiative. Its product design requires published releases to include inspectable benchmark evidence, downloadable data, reproducible charts, and immutable dataset versions without depending on a runtime service.

The JS 1.0 source repository contains the published benchmark JSONL results, fixture projects and reference findings, chart manifests, article-visual notes, generated HTML visualizations, historical visual variants, and Apache 2.0 license. Keeping these artifacts only in a separate repository would make the website incomplete and introduce an external availability dependency.

## Decision

Import the complete contents of the upstream repository into the top-level `snyk-vulnbench-js-1.0/` directory as an immutable vendored snapshot.

The import will:

- Use the exact upstream commit recorded above.
- Include every tracked upstream file and directory.
- Exclude upstream Git metadata; `snyk-vulnbench-js-1.0/` will not be a nested repository.
- Add a clearly identified local provenance record containing the source URL, commit SHA, tree SHA, commit timestamp, and import date.
- Preserve upstream file contents and paths unchanged.
- Remain available through an ordinary clone of this repository with no submodule or network initialization step.

## Rationale

A bare clone has no working tree and therefore cannot provide files to the website build. A shallow nested clone leaves a second Git repository inside this one and does not make its working-tree contents reliably part of the parent repository. A submodule keeps the external repository as the source of truth and adds checkout, CI, deployment, and long-term availability dependencies.

A vendored snapshot best matches the selected ownership model: this repository owns the published copy while retaining exact upstream provenance. The upstream repository has only two commits and a small data footprint, so importing its Git history would add complexity without meaningful value.

## Data boundary

The imported directory is the archival source of evidence for JS 1.0, not the website application's runtime schema.

Future website implementation will:

1. Read the imported source during the build.
2. Validate the source and reconstruct published headline values.
3. Transform it into typed, versioned release assets for narrative pages and the explorer.
4. Publish only the assets needed by each route, with large finding-level data split or compressed as required.

This boundary preserves the original research artifacts while allowing the website's release manifest and public data contracts to evolve independently.

## Immutability and corrections

Files in the imported snapshot must not be silently rewritten after publication. If JS 1.0 data requires a correction:

- Preserve the original snapshot.
- Import the corrected source as a new dataset patch version.
- Record the source revision, affected values, and reason for the correction.
- Update the release manifest and correction history explicitly.
- Keep existing stable release URLs valid.

Website-only derived assets may be regenerated when build tooling changes, provided validation proves that their scientific values and provenance remain unchanged.

## Verification

The import is complete when:

- No nested `.git` directory exists.
- Every file from upstream commit `7c944ea438a31ea4cbd6803f1bb9560d01f932e5` is present.
- Imported upstream file hashes match the recorded upstream tree.
- The provenance record identifies upstream tree `e1490c821be5be869b91e482eb037e3f2672f432`, committed at `2026-06-09T06:39:46Z`.
- The result is available after a normal clone with no recursive checkout.
- The repository still contains the upstream Apache 2.0 license.

## Alternatives rejected

- **Bare clone:** no checked-out files for build-time use.
- **Shallow nested clone:** creates an embedded repository and unreliable parent-repository tracking.
- **Git submodule:** retains an external source-of-truth and availability dependency.
- **Git subtree:** workable, but its synchronization machinery and imported history are unnecessary for an immutable two-commit release snapshot.
